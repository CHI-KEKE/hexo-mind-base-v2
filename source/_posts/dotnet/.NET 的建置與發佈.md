<!-- tab `Microsoft.NET.Sdk` 是什麼-->


`<Project Sdk="Microsoft.NET.Sdk">` 裡的 `Microsoft.NET.Sdk` 是**專案建置 SDK**：它提供 MSBuild 的預設屬性、檔案納入規則與 restore／build／publish 等建置目標。MSBuild 評估專案時會隱含載入這套 SDK 的設定。它在**開發或建置機器**上發揮作用，不是部署到目標機器後用來執行程式的 Runtime；也不代表產物必定使用 .NET Core。

同一個 `Microsoft.NET.Sdk` 專案，可以用 `<TargetFramework>net462</TargetFramework>` 指定編譯給 .NET Framework 4.6.2，也可以用 `net8.0` 指定編譯給 .NET 8。能否建置還取決於所需的參考組件、套件及專案專屬 targets 是否齊全。這也說明**建置用 SDK**、**編譯目標框架**、**執行用 Runtime** 是三個不同層次。[Microsoft：.NET 專案 SDK](https://learn.microsoft.com/en-us/dotnet/core/project-sdk/overview)

| 專案設定 | 建置時使用 | 產物的執行目標 |
| --- | --- | --- |
| `Sdk="Microsoft.NET.Sdk"` + `TargetFramework=net462` | 專案 SDK 的建置規則 | .NET Framework 4.6.2 |
| `Sdk="Microsoft.NET.Sdk"` + `TargetFramework=net8.0` | 專案 SDK 的建置規則 | .NET 8 |


<!-- endtab -->

<!-- tab `.NET Framework` 與 `.NET Core` 具體差在哪裡？-->

「.NET Framework」說的是程式**要以哪套 .NET 平台執行**


它們是**不同的 .NET 實作與執行平台**，不只是 Runtime 版本號不同。除了各自的執行環境，還有不同的基礎函式庫與可用 API、應用程式模型、作業系統支援和部署方式。`.NET Framework 4.8` 不會因為數字大於 `.NET Core 3.1`，就成為後者的升級版。Microsoft 從 **.NET 5** 起拿掉名稱中的「Core」；本文的「現代 .NET」指 .NET Core 及後續的 .NET 5+，而 .NET Framework 仍是另一條產品線。[Microsoft：移轉概覽](https://learn.microsoft.com/en-us/dotnet/core/porting/framework-overview)

| 面向 | .NET Framework | .NET Core／現代 .NET |
| --- | --- | --- |
| 執行環境 | Windows 上的 .NET Framework CLR 與函式庫 | .NET Core／現代 .NET Runtime 與其函式庫 |
| 作業系統 | Windows | 平台支援 Windows、Linux、macOS；若程式使用 Windows 專屬 API，仍只能在 Windows 執行 |
| 目標框架代號 | `net48`、`net462` 等 | .NET Core 常見 `netcoreapp3.1`；.NET 5+ 常見 `net8.0` 等 |
| Web 應用程式 | 傳統 ASP.NET 使用 `System.Web`、`Global.asax`，常由 IIS／IIS Express 承載 | ASP.NET Core 使用自己的要求處理管線與宿主；不是把傳統 ASP.NET 專案換個 TFM 就能取得 |
| 部署方式 | 目標 Windows 機器需具備相容的 .NET Framework | 可依賴已安裝 Runtime，或將 Runtime 一起發布為 self-contained 產物 |

例如 SCM ApiV2 的網站使用 `System.Web`，目標是 .NET Framework 4.6.2。即使把它的 `.csproj` 轉成 SDK 格式並保留 `net462`，網站依舊需要原本的 ASP.NET／IIS 執行環境；如果改成 `net8.0`，還要移轉不相容的 API、套件與網站宿主。**專案格式決定「怎麼建」，目標框架與應用程式模型決定「建給誰跑、怎麼啟動」。**

<!-- tab 為什麼 .NET Core／現代 .NET 專案多用 SDK 格式？-->

SDK 省掉的是重複的檔案清單與通用建置樣板，**沒有取消依賴關係**。需要特殊納入或排除規則時，仍可在 `.csproj` 明確設定。


「SDK 格式」說的是 `.csproj` **如何描述建置工作**
SDK 格式專案也可以指定 `net48`，編譯給 .NET Framework 4.8 使用。

舊式 `.csproj` 常把每個原始碼檔案逐一列出，例如 `<Compile Include="Program.cs" />`。新增或搬移檔案時，專案檔也可能要跟著更新。SDK 格式把**常見規則交給 SDK**：`<Project Sdk="Microsoft.NET.Sdk">` 讓 MSBuild 自動載入 SDK 的建置設定；預設以遞迴規則納入專案目錄下的 `.cs` 檔，也處理常見資源檔，並排除 `bin`、`obj` 等輸出目錄。於是 `.csproj` 主要留下目標框架、套件參考、專案參考及特殊設定。

```xml
<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <TargetFramework>net8.0</TargetFramework>
  </PropertyGroup>
  <ItemGroup>
    <ProjectReference Include="..\Shared\Shared.csproj" />
    <PackageReference Include="Some.Package" Version="1.2.3" />
  </ItemGroup>
</Project>
```



| 比較面向 | SDK 格式專案 | 常見的舊式 .NET Framework 專案 |
| --- | --- | --- |
| `.csproj` 寫法 | 常以 `<Project Sdk="Microsoft.NET.Sdk">` 開頭，由 SDK 提供預設建置規則，檔案較精簡 | 常明列檔案、參考、建置設定與 MSBuild imports，檔案通常較長 |
| 目標框架寫法 | 常用 `<TargetFramework>net8.0</TargetFramework>`；也可寫 `net48` | 常用 `<TargetFrameworkVersion>v4.8</TargetFrameworkVersion>` |
| 常見工具入口 | `dotnet restore`、`dotnet build`、`dotnet publish` | Visual Studio 的 `MSBuild.exe`；套件還原須看 `PackageReference` 或 `packages.config` |
| 執行平台 | **由 TargetFramework 決定**，不能只看專案格式 | .NET Framework 執行環境限 Windows |

例如下面仍是 **SDK 格式**，但目標平台是 **.NET Framework 4.8**：

```xml
<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <TargetFramework>net48</TargetFramework>
  </PropertyGroup>
</Project>
```

相反地，若看到 `<TargetFrameworkVersion>v4.8</TargetFrameworkVersion>`，通常代表舊式專案檔。實際能否使用 `dotnet build`，還要看專案使用的 targets、工作負載及開發機是否具備所需元件。**先辨認專案格式，再辨認目標框架，最後確認工具鏈**，才能解釋為何同是 `.csproj`，建置指令卻不同。

<!-- tab 舊版 dotnet 專案用 SDK 格式 能跑嗎-->


我們可以把 csproj 的 SDK 格式想成「建置規則的預設套件」，它可以自動找出專案目錄裡一般的 `.cs` 檔，省去逐筆寫 `<Compile Include="...">`，然而它不知道這個舊版框架的專案原本的網站如何處理 IIS、內容檔、設定轉換與發布，因此「不用列出每個 `.cs`」和「其他建置行為完全相同」是兩件事


| SCM ApiV2 原本的設定 | 只加 `Sdk`、刪 `.cs` 清單之後還要確認什麼 |
| --- | --- |
| `<TargetFrameworkVersion>v4.6.2</TargetFrameworkVersion>` | 改用 SDK 格式的 `<TargetFramework>net462</TargetFramework>`，執行目標仍是 .NET Framework 4.6.2 |
| 專案明列內容檔、資源檔與 `packages.config` | SDK 也會預設納入部分檔案；要檢查是否重複、是否保留原本的發布用途 |
| 網站組件輸出到 `bin\` | SDK 可能在輸出路徑附加 `net462`；要確認 IIS 讀到的仍是預期的網站組件 |
| 匯入 `Microsoft.WebApplication.targets`，另有 SlowCheetah 設定轉換 | 要驗證這些原有建置目標和 SDK 預設目標能否共同運作，且轉換後的設定檔正確 |

**所以合理的預期是一般 `.cs` 檔案清單可以刪，但網站專屬設定仍須逐項比對。** 即使編譯成功，也要再用 IIS／IIS Express 啟動網站，檢查實際請求與發布產物，才能說「轉換後照常運作」

<!-- tab 整體流程-->


```bash
.sln / .csproj + 原始碼 + NuGet 設定
             │
             ▼
restore：解析相依套件，取得建置需要的檔案
             │
             ▼
build：依目標框架與組態編譯，產生組件
       ├─ run：啟動應用程式
       ├─ test：執行測試
       └─ publish：整理目標環境需要的交付檔案
```


這是概念順序，一般 SDK 專案的 `dotnet build` 預設會 restore，而 `dotnet run`、`dotnet test`、`dotnet publish` 也會執行各自需要的前置步驟。若前置步驟已完成，可視情況使用 `--no-restore`、`--no-build`，但目標框架、組態、Runtime Identifier（RID）等條件須一致


| 指令 | 核心問題 | 主要行為 |
| --- | --- | --- |
| `restore` | 建置需要哪些套件？ | 解析 NuGet 相依關係，取得缺少的套件 |
| `build` | 程式能否編譯？ | 建置專案及其參考，產生組件 |
| `run` | 程式能否啟動？ | 必要時建置，再啟動應用程式 |
| `test` | 測試是否通過？ | 必要時建置，再執行測試 |
| `publish` | 要交付哪些檔案？ | 必要時建置，整理部署目錄 |

<!-- tab MSBuild-->


MSBuild 評估這些設定，並執行對應的 targets。對 SDK 專案，`dotnet build` 使用 .NET SDK 內的 MSBuild，大致相當於 `dotnet msbuild -restore`。`-c Release`、`-r win-x64`、`-p:Name=Value` 等參數會改變這次建置的屬性。


**SDK** 提供開發建置工具

**目標框架**（如 `net8.0`、`net48`）決定編譯時可用的 API


**Runtime** 是目標機器執行程式所需的環境。裝有 Runtime 不等於能建置，裝有 SDK 也不代表舊式專案所需的 Visual Studio 元件都齊全

<!-- tab Restore-->


```bash
dotnet restore .\WindowsTaskManager.csproj
```

Restore 的意思是**依照專案已記錄的套件需求，把建置材料備齊**，流程依序是


1. **讀需求**：評估 `.csproj`、`ProjectReference`、目標框架與 NuGet 來源設定（`nuget.config`），找出直接依賴的套件
2. **算完整依賴**：解析套件彼此需要的其他套件、版本與目標框架相容性，得到可供建置的依賴圖
3. **找檔案**：檢查本機快取，缺少時才向設定的 NuGet 來源取得，因此可能需要網路、內網連線或認證
4. **記結果**：`PackageReference` 專案通常將套件放在全域套件快取，並產生 `obj\project.assets.json`，讓後續 build 知道實際使用哪些套件組件。Restore 不會替你新增或升級專案檔裡的套件參考



## 為什麼新版專案用 `dotnet restore`，舊版專案用 `nuget restore`？


關鍵是**套件參考格式**，不是「.NET Core 可以、.NET Framework 不可以」，例如 Livebuy API 是 `Microsoft.NET.Sdk.Web`、目標 `net8.0`，在 `.csproj` 用 `PackageReference` 記錄套件，而 SCM ApiV2 網站則用 `packages.config` 記錄套件，例如 `Autofac` 4.1.1，並在 `.csproj` 用 `HintPath` 指向 solution 的 `packages\Autofac.4.1.1\...` DLL



| 專案 | 套件需求寫在哪裡 | 合適的還原入口 | 還原後要看到什麼 |
| --- | --- | --- | --- |
| Livebuy API | `.csproj` 的 `PackageReference` | `dotnet restore`；或讓 `dotnet build` 隱含還原 | 全域套件快取有套件，專案產生 `obj\project.assets.json` |
| SCM ApiV2 | 各專案的 `packages.config`，搭配 `.csproj` 的 `HintPath` | `nuget restore` 或支援版本的 Visual Studio MSBuild 明確啟用 `RestorePackagesConfig=true` | solution 的 `packages` 目錄有對應版本，`HintPath` 找得到 DLL |


```bash
# Livebuy：在其 src 目錄，明確還原 solution
dotnet restore .\Nine1.Livebuy.Web.Api.sln

# SCM ApiV2：在其 solution 目錄，依 packages.config 還原
nuget restore .\NineYi.Scm.ApiV2.sln
```

`dotnet restore` 主要處理 `.csproj` 裡的 `PackageReference`，**不會替舊專案還原 `packages.config` 所列的套件**，因此對專案例如 SCM ApiV2 執行這個指令，可能在評估舊式專案時失敗，也可能結束卻沒有補齊 `packages` 目錄，無法只看指令執行結束，就認定原建置依賴已備齊


另外 `nuget restore` **不是只能處理** `packages.config`，也能處理部分 `PackageReference` 專案，只是對 SCM ApiV2 的現況，它是合適的選擇


若本機已有全部套件，還原可能不需重新下載，若缺少套件新舊專案都可能從網路拉取，如果來源無法存取，**都可能因網路或認證失敗**
