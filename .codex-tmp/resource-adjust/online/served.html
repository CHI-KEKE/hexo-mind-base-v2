Kubernetes 資源調整：從配額到可用副本

服務想增加一個副本，卻被資源配額擋下。調整 CPU 時，需要分清楚允許申請多少、Node 還能排入多少，以及程式當下實際用了多少。

原始錯誤訊息

Pod 建立失敗紀錄 
pods "promotion-web-api-76d9db5667-8wxfr" is forbidden: exceeded quota: default-4w42q, requested: limits.cpu=2250m, used: limits.cpu=7250m, limited: limits.cpu=8:Deployment does not have minimum availability.

這段紀錄同時呈現三個層面：ResourceQuota 超限、Pod 建立遭到拒絕，以及 Deployment 未達最低可用性。先解讀配額欄位，再檢查 Deployment 的實際狀態。

訊息欄位 意義
pods "promotion-web-api-76d9db5667-8wxfr" is forbidden Kubernetes API Server 拒絕這次 Pod 建立請求，這個新 Pod 尚未成功建立。
exceeded quota: default-4w42q Namespace 中名為 default-4w42q 的 ResourceQuota 不允許這次新增。
requested: limits.cpu=2250m 這次新增會計入 2250m，即 2.25 CPU 的 limits.cpu 配額。此處 requested 是配額增量，不是 resources.requests.cpu。
used: limits.cpu=7250m 已有 7250m，即 7.25 CPU 的 limits.cpu 被計入配額；不是當下實際消耗 7.25 CPU。
limited: limits.cpu=8 Namespace 的 limits.cpu 配額上限是 8 CPU，即 8000m。
Deployment does not have minimum availability Deployment 的可用副本未達最低要求，需再查看 replicas、Available condition 與更新策略。

配額計算：7250m + 2250m = 9500m > 8000m。原本只剩 750m 的 limits.cpu 配額，這次新增需要 2250m，因此超出 1500m。即使 Node 還有空閒 CPU，也無法繞過這項配額檢查。

例如期望 3 個副本而目前只有 2 個可用，是否未達最低可用性，仍要看更新策略允許的 maxUnavailable。Available 也不等於 Running：副本需就緒並符合 minReadySeconds 等條件。此錯誤未提供完整 Deployment 設定，不能直接判定實際期望與可用副本各是多少。

Kubernetes：ResourceQuota；Kubernetes：Deployment 可用性

調整設定後，要一起觀察哪些變化

觀察項目 應核對的內容
resource request 下降／上升 調整前後的 Pod requests、排程容量，以及 HPA 的 CPU Utilization 分母是否改變。
Node 數量減少／增加 是否啟用 Node 自動擴縮、是否有排不進去的 Pods，以及是否符合擴容或整併條件；request 與 Node 數量不是固定比例。
是否 Throttled 是否用完 CPU limit 對應配額；同時區分 Node CPU 競爭與應用程式負載。
limits 是否正常套用 比對 chart、pipeline 產出、Deployment template 與實際 Pod 的 resources，不能只看設定檔。

原始維運紀錄

原稿記錄曾遇到 limits 沒有正常套用，當時在 Rancher 手動調整 limits；另記錄 chart 檔的 limits 需要使用 pipeline v1.3.3-stable 以上版本。

以上是內部環境的原始觀察，不是 Kubernetes 的通用版本要求。尚未查核內部討論的完整內容，也未確認目前 pipeline 是否仍有相同限制。

內部討論來源：資源調整與 pipeline

request 寫 500m，代表什麼

request: 500m 表示排程時要計入 0.5 CPU 的需求，不是建立一台只有 0.5 CPU 的小主機。以下假設 Pod 只有一個應用容器。

容器的 CPU 設定 
resources:
  requests:
    cpu: 500m
  limits:
    cpu: 2000m
當下情況 可能的 CPU 使用量
沒什麼請求 可能只用 20m，不會固定消耗 500m。
工作變多，Node 有空閒 CPU 可以用到 800m、1500m。
用完 2000m limit 對應的 CPU 配額 受到 CPU limit 限速，等待後續配額週期。

這個容器申請 0.5 CPU 的排程容量，最高允許使用 2 CPU；實際使用量取決於工作量與可用資源。一般情況下，這不代表綁定半顆專屬 CPU。

request 的用途 影響
排入 Node Scheduler 確認單台 Node 的剩餘可排程容量足以容納 500m，並符合其他資源與排程條件。
CPU 發生競爭 影響容器取得 CPU 時間的相對權重，不是忙碌時固定限制在 500m。
HPA 使用 CPU Utilization request 是使用率分母，例如實際 400m ÷ request 500m = 80%。

訂位容量與實際使用量

可以把 request 想成訂位，實際 CPU 使用量則是當下有多少人在使用。以下假設一台 Node 扣除其他需求後，有 4000m 可供這批 Pods 排程，且只考慮 CPU。

情境 結果
每個 Pod request 為 500m 4000m ÷ 500m = 8，最多容納 8 個。
8 個 Pod 當下各只用 10m 實際合計 80m，但 requests 合計仍是 4000m。
再新增第 9 個相同的 Pod 這台 Node 的 CPU 排程容量已滿，需找其他符合條件的 Node。

排程時按申報的需求計算，可以避免因平時使用量低就把太多 Pods 塞在同一台 Node。實際還要考慮 Memory、Pod 數量上限、系統保留資源及其他排程限制。

request 設太大或太小的影響

設定 requests.cpu: 500m 後，Scheduler 尋找有足夠容量且符合條件的 Node。成功排入後，這份需求就會被計入；找不到合適 Node 時，Pod 可能維持 Pending。

CPU request 若設得過大，會壓縮共用這批 Node 的其他服務新增 Pod 或擴容的空間。即使 Node 實際 CPU 使用率只有 10%，也可能因 requests 接近可排程容量而放不進新 Pod。若啟用 Node 自動擴縮，還可能提早新增 Node、增加成本。

request 設得過小，則可能讓太多 Pods 擠在一起，忙碌時競爭 CPU。request 是容量規劃與分配的依據，limit 是執行時的使用上限。

Kubernetes：CPU 資源分配；Kubernetes：HPA 計算方式

排程只剩 1m，為什麼還能使用更多 CPU

假設新的 Pod request 是 500m、limit 是 1000m，排入後 Node 的排程容量只剩 1m。這個數字代表尚未被 requests 占用的容量，不是 CPU 當下只剩 1m 能運算。

以下假設 Node 可排程 CPU 共 2000m。其他 Pods 雖然申報較高的需求，當下未必全部用完。

項目 CPU request 當下實際使用示例
其他 Pods 合計 1499m 600m
新 Pod 500m 1000m
合計 1999m 1600m

排程容量剩下 2000m − 1999m = 1m，但實際使用只有 1600m，所以此例中新 Pod 仍可使用到 1000m。這是假設當下有足夠 CPU 的示例，limit 不保證一定能取得這麼多 CPU。

其他 Pods 忙起來，是否就會 throttling

情況 發生什麼事
Node 的 CPU 不夠大家同時使用 發生 CPU 競爭，容器需等待 CPU 執行時間；request 影響分配權重，即使未達 limit 也可能變慢。
容器用完自己的 CPU limit 配額 發生 CPU throttling，等待後續配額週期；即使 Node 還有空閒 CPU，也可能發生。

其他 Pods 忙起來，不代表這個 Pod 一定觸發 limit throttling。它可能只是分到的 CPU 時間減少，兩種情況也可能同時存在。request 500m 並不是一忙起來就強制限制在 500m。

Kubernetes：requests 與 limits 的執行方式

Node 不屬於某個 namespace

Node 屬於整個 Cluster，namespace 本身沒有固定分配幾台 Node。同一台 Node 可以同時執行不同 namespace 的 Pods。

Node 可能執行的 Pods
Node 1 namespace A 的 Pod、namespace B 的 Pod
Node 2 namespace A 的 Pod、namespace C 的 Pod
Node 3 namespace B 的 Pod

Kubernetes：Namespaces

Namespace 配額不是預留的 Node 容量

Namespace 的 CPU／Memory request 上限通常由管理員透過 ResourceQuota 設定，不是每個 namespace 自動就有。以下是 namespace A 的配額片段。

ResourceQuota 的 hard 設定片段 
hard:
  requests.cpu: "4"
  requests.memory: 8Gi

受配額計算的 Pods，其 CPU requests 合計不得超過 4 CPU，Memory requests 合計不得超過 8Gi。這是申請資源總額的上限，不表示已預留 4 CPU，也不表示分配了幾台 Node。

阻擋位置 情況 結果
配額檢查 namespace 配額已滿，即使 Node 還有空間。 新 Pod 的建立請求被拒絕，不是先建立成 Pending。
排程 配額允許建立，但找不到符合需求的 Node。 Pod 已建立，可能維持 Pending。

從配額檢查到 Node 擴容

Pod 建立與排程的不同關卡 

    flowchart TB
Create["建立 Pod 的請求"] --> Quota{"配額允許嗎？"}
Quota -->|否| Reject["拒絕建立：Forbidden"]
Quota -->|是| Admit["Pod 建立成功"]
Admit --> Fit{"有合適 Node 且容量足夠？"}
Fit -->|是| Schedule["排程到 Node"]
Fit -->|否| Pending["Pending：等待排程"]
Pending --> Auto{"已啟用且可擴容？"}
Auto -->|是| New["新增合適 Node"]
New --> Fit
Auto -->|否| Wait["等待容量釋放或條件改善"]

由上往下閱讀，菱形是檢查條件，分支標明是／否。這張圖聚焦資源配額與容量，不列出其他可能拒絕建立的驗證或政策。

啟用 Cluster Autoscaler 或 Karpenter 等 Node 自動擴縮工具後，工具可評估排不進去的 Pods，判斷新增 Node 能否解決需求；符合擴容設定且未達上限時，才新增合適 Node，再由 Scheduler 排程。

不是所有 Pending 都會觸發加 Node。排程條件無法滿足、已達擴容上限，或雲端容量不足，都可能無法擴容。減少 Node 則還需符合整併、搬移與中斷限制，不能只看 request 是否下降。

Kubernetes：ResourceQuota；Kubernetes：Node 自動擴縮

CPU Utilization 的分母是 request

HPA 若使用 CPU Utilization 百分比，會將 CPU 使用量相對於 request 計算，再依符合條件的 Pods 彙整。以下用單一容器、資料齊全的 Pod 說明。

單一 Pod 的使用率示意 
HPA CPU 使用率 = 實際 CPU 使用量 ÷ CPU request × 100%
實際 CPU 使用量 CPU request 相對使用率
400m 500m 80%
400m 1000m 40%

提高 request，一方面讓每個 Pod 占用更多排程容量，另一方面可能降低 HPA 算出的使用率。實際結果需一起看 request／limit、replicas／HPA、Node 規格與自動擴縮設定；不能直接推論 request 加倍就會多幾台 Node。

min 2、max 4 需要多少排程容量

假設每個 Pod 的 CPU request 合計為 500m，HPA 設定 minReplicas: 2、maxReplicas: 4。這表示期望副本數在 2～4 之間調整，不保證當下每個副本都能成功排程或就緒。

Pod 副本數 CPU request 總需求
2 1000m
3 1500m
4 2000m
元件 負責的事情
HPA 根據指標與設定調整副本數；啟動時的初始數量也受 Deployment replicas 影響，HPA 會週期性調整。
Scheduler 選擇 Node；兩個 Pods 可以在同一台，也可以分布在不同 Node。成功排入的 request 會占用該 Node 的排程容量。
Node Autoscaler 評估是否需要及能否調整 Node 容量，不由 HPA 直接建立 Node。

只夠一個 Pod 時，第二個會等待

假設服務需要 2 個 Pods，每個 request 為 500m。只有一台符合條件的 Node 還有 500m 排程容量，其他 Node 都放不下。先排入的 Pod 可以啟動，另一個會因容量不足而等待。

兩個期望副本，只有一個能排入 

    flowchart TB
Desired["期望 2 個 Pods：各 request 500m"] --> A["Pod A"]
Desired --> B["Pod B"]
subgraph Node["唯一可用 Node：原剩餘 500m"]
Running["Pod A 排入：啟動後 Running"]
end
A -->|占用 500m 排程容量| Running
B -->|已無足夠容量| Pending["Pod B：Pending / Insufficient cpu"]

兩個分支代表不同 Pod，不表示 HPA 指定誰先成功。假設沒有搶占等額外行為；Running 的 Pod 仍需通過就緒條件才能正常接流量。

HPA 的 minReplicas: 2 是最低期望副本數，不是保證有 2 個可用副本。若 Node 自動擴縮允許新增合適 Node，第二個 Pod 才有機會排入；否則等待容量釋放。

CPU 容量不能跨 Node 湊給同一個 Pod。例如兩台 Node 各剩 250m，合計雖然是 500m，仍無法容納單一 request 為 500m 的 Pod。

Kubernetes：Horizontal Pod Autoscaling

執行階段與就緒條件分開看

欄位 意義
Running Pod 的執行階段。容器已建立，至少一個容器仍在執行，或正在啟動／重啟；不代表所有容器都健康。
Ready Pod 的就緒條件。一般情況需各容器就緒，並符合已設定的 readiness gates 等條件，才適合接收一般 Service 流量。

Running 期間，Ready 可以來回變化 

    flowchart TB
Pending["Pending：尚未進入執行階段"] -->|排程及啟動完成| Unready["Running + Ready=False"]
Unready -->|就緒檢查與條件通過| Ready["Running + Ready=True"]
Ready -->|就緒檢查達失敗門檻| Unready

這是簡化的典型啟動與就緒變化，不是完整 Pod 生命週期。Ready 成為 True 後，Pod 仍是 Running；就緒失敗也不一定使程式退出。

三種 Running 但未 Ready 的情境

情境 程式為何仍 Running 為何未 Ready
剛啟動，還在初始化 API 程式已執行，正在載入設定或預熱資料。 readiness 可能尚未連通或回傳 503，完成初始化並通過檢查後才就緒。
必要依賴暫時故障 API 程式仍存活，也能接受 HTTP 連線，但必要資料庫連線失敗。 只有當 readiness 邏輯包含該依賴檢查時，才會反映成失敗，例如回傳 503；Kubernetes 不會自行判斷資料庫健康。
服務太忙，健康檢查逾時 CPU 競爭、throttling 或執行緒池耗盡，但程式沒有退出。 /health/ready 未能在設定時間內回應，失敗達門檻後變成未 Ready。

一般 Service 會在就緒狀態更新後，停止將新流量導向未 Ready 的 Pod。readiness 失敗本身不會重啟容器，恢復通過檢查後可再次接流量；這不表示既有連線會立刻中斷。

沒有設定 readinessProbe 時，Kubernetes 不會自動驗證 API 的業務功能，容器啟動後通常會被視為就緒；Pod 仍受其他就緒條件影響。本文描述一般 Service 行為，未涵蓋 publishNotReadyAddresses 等特殊設定。
