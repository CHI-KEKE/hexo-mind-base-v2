先分清 EKS 與應用程式的管理責任

Amazon EKS 是 AWS 提供的受管 Kubernetes 服務。自行架設 Kubernetes 時，Control Plane 的建置、高可用、版本升級與故障處理都需自行負責；使用 EKS 後，由 AWS 維運受管 Control Plane，應用程式與叢集使用方式仍需規劃。

範圍 自行架設 Kubernetes 使用 Amazon EKS
Control Plane 管理 kube-apiserver、etcd、scheduler、controller manager。 AWS 維運受管 Control Plane；仍需規劃版本升級時機與相容性。
Worker Nodes 管理 Node A、Node B、Node C 等工作節點。 EC2 Node Group 仍有節點維護責任；實際責任依運算模式不同。
應用與容量 管理 Deployment、Service、Ingress、Pod。 仍需管理上述資源、CPU／Memory requests & limits、HPA 與 Container Image。
權限與觀測 規劃網路、授權及監控。 仍需規劃 IAM、Security Group、Monitoring 與 Node Group。

Controller 與 Target Type 的差異

AWS Load Balancer Controller 會依 Kubernetes 資源設定協調 AWS 的負載平衡資源與 targets。它屬於控制層，不是每筆 API 請求都會穿過的 HTTP proxy。

Target Type ALB 的直接目標 Pod 重建時的解讀
ip Pod IP 等 IP targets。 若由 Controller 管理 Pod targets，Pod 重建後，10.x.x.x 等註冊目標可能跟著更新。
instance EC2 Instance 的 Service NodePort。 不能把 Target Group 的 Instance targets 當成 Pod IP；Pod 變化由叢集內 Service 對應處理。

AWS Load Balancer Controller：流量模式

觀察紀錄：兩台 Instance 與 32080

原始紀錄中的 Target Group 使用 Instance，流量送往兩台 EC2 Instance 的 32080 port。這個 port 落在 Kubernetes 預設 NodePort 範圍 30000–32767，符合 Worker Node／NodePort 的可能架構，但仍需比對 EC2 身分與 Service 設定。

實線表示原稿記錄的入口關係，虛線表示尚待查證的叢集內路徑。若 NodePort 指向應用 Pod，後面就不會有這層 Ingress Controller；Service 是邏輯路由關係，不是額外 HTTP proxy。

一種可能是 ALB 將不同 domain 的流量統一交给叢集內 Ingress Controller，再分流到 Shopping、Payment、Member 等服務。需先找到 32080 所屬 Service，再查看 selector、EndpointSlice 與 IngressClass，才能確定是否符合這個假設。

Annotations 由對應 Controller 解讀

Kubernetes Resource 的 metadata.annotations 是附加的 Key-Value 資訊。Ingress 上的 annotations 可供對應 Controller 調整路由或 AWS 資源，但不同 Controller 的設定不能混為一談。

設定示例 用途與限制
alb.ingress.kubernetes.io/target-type: instance AWS Load Balancer Controller 的目標模式，instance 模式需要適用的 NodePort／LoadBalancer Service。
alb.ingress.kubernetes.io/actions.* 定義 ALB 自訂 action，需讀取實際 JSON；不是任意刪除 Header 的設定。
nginx.ingress.kubernetes.io/proxy-read-timeout: "60" NGINX Ingress 的讀取逾時示例，不表示會刪除 Header，也不適用於 ALB Controller。

從 Windows 連線到 EKS

連線順序是 Windows 上以 AWS CLI 驗證 IAM 身分，再透過 aws eks update-kubeconfig 寫入 ~/.kube/config，最後由 kubectl 連線至 EKS Kubernetes API Server。以下是操作範例，佔位符需替換為實際值。

  1. 確認工具與 AWS 身分 
aws --version
aws sts get-caller-identity
# 使用 AWS SSO / IAM Identity Center 時
aws sso login --profile <公司-profile>
aws sts get-caller-identity --profile <公司-profile>

身分查詢成功會回傳 Account、Arn 等資訊。後續指令應持續使用同一個已確認的 profile。

  1. 查詢叢集與確認 kubectl 
aws eks list-clusters --region <region>
# 使用具名 profile 時
aws eks list-clusters --region <region> --profile <profile>
kubectl version --client

若尚未安裝 kubectl，可依 AWS：安裝 kubectl 處理。

  1. 建立 kubeconfig 
# 原稿範例：Cluster = public-eks-hk，Region = ap-east-1
aws eks update-kubeconfig --region ap-east-1 --name public-eks-hk
# 使用具名 profile 時，改用此指令
aws eks update-kubeconfig --region ap-east-1 --name public-eks-hk --profile <profile>
kubectl config current-context
kubectl get nodes

預設會更新 C:&lt;帳號>.kube。如果 EKS API Endpoint 是 private-only，電腦必須能連入 VPC，例如透過公司 VPN；IAM 身分驗證成功也不代表已具備 Kubernetes 資源讀取權限。AWS：建立 kubeconfig

  1. 找出 NodePort 對應服務 
kubectl get svc -A | Select-String 32080
kubectl get svc <service-name> -n <namespace> -o yaml
kubectl get endpointslices -n <namespace> -l kubernetes.io/service-name=<service-name> -o yaml
kubectl get ingressclass
kubectl get ingress -n <namespace> -o yaml

檢查 Service 的 nodePort、targetPort、selector，再比對 EndpointSlice 與實際 Pods。Ingress 則查看 spec.ingressClassName、Host、Path、backend 與 annotations；如果確認有 NGINX，再檢查該 Controller 的 ConfigMap 及適用的 Header 設定。
